LLM Evals Explained: How to Measure RAG and Q&A Bots (What I Learned Building LLM-EvalHub)

"Looks good to me" is not an evaluation. Here is how to measure RAG and Q&A bots properly, avoid judge biases, and close the loop between diagnosing failures and testing improvements.

Table of Contents

Introduction: Why "It Looks Good in the Demo" Is Not an Evaluation

When building a Retrieval-Augmented Generation (RAG) app or Q&A bot, testing often begins casually: you draft a prompt, index two PDF documents, ask three questions in a web playground, and decide it works.

Then real users arrive. Someone asks an edge-case query that retrieves the wrong policy chunk. Someone asks about an unmentioned topic, and the bot invents a fictional procedure. Tweak the prompt to patch that single query, and you risk silently breaking ten queries that worked yesterday. Checking three hand-picked prompts is an impression, not an evaluation.

I am still learning this discipline myself, and building tools is how I am learning it. To explore these challenges empirically, I built an open-source evaluation platform: LLM-EvalHub. In this guide, I share the practical lessons I learned: how to isolate pipeline layers, what metrics really mean, how to avoid LLM judge biases, and how to verify whether your modifications actually helped.

LLM evals in 60 seconds

  • The Core Shift: Traditional unit tests check binary pass/fail assertions. LLM evals measure distributions of open-ended quality over structured datasets because there is rarely one single correct string.
  • Separate the Layers: Measure retrieval (did you surface the right passage?) independently from generation (did the model answer faithfully from it?). Conflating them leads to tuning prompts for retrieval failures.
  • Unavailable Is Not Zero: If a test case lacks a reference answer, report correctness as unavailable rather than 0.0. Averaging missing values as zeroes corrupts model rankings.
  • Calibrate LLM Judges: Judges suffer from position bias, verbosity inflation, and self-preference. Measure agreement against blind human labels using Cohen's kappa (κ) before trusting their scores.
  • Close the Product Loop: A leaderboard only shows who scored highest. A complete evaluation loop diagnoses failure root causes, applies configuration fixes, and verifies before/after verdicts.

What Are LLM Evals, and How Are They Different from Classic Testing?

In deterministic software, unit tests check exact equality (assert calculate_tax(100) == 10.0). In classic machine learning, models predict fixed class labels evaluated against loss functions on test splits.

Generative LLMs break both paradigms:

  • Open-ended outputs: If the ground truth is "The warranty lasts for two years," a model might respond with "Your device is protected for 24 months." String equality fails despite perfect semantic accuracy.
  • Stochastic generation: Unless temperature is zero with fixed seeds, wording varies across runs.
  • Multi-dimensional quality: An answer can be polite and well-phrased while being factually wrong, or accurate while blowing past latency budgets.

An LLM eval is a systematic testing framework consisting of: a curated dataset of inputs and reference answers, a harness executing candidates through identical prompt templates, and scoring evaluators that quantify performance across multiple dimensions.

The Three Layers of a RAG or Q&A System to Measure

When a Q&A bot produces a flawed answer, beginners almost always blame the generative model. They rewrite the prompt, add capital letters saying "BE FACTUAL," and test again.

In reality, a RAG application is a multi-stage pipeline. A failure at the retrieval step corrupts every downstream calculation. To measure a system cleanly, you must evaluate three distinct layers:

  1. Retrieval Layer: Did the search mechanism (vector similarity, BM25, or hybrid search) locate the right passages from your knowledge base? If the retriever surfaces irrelevant text, the generator has no factual grounding.
  2. Generation Layer: Given the retrieved context, did the LLM extract the correct facts, answer the question directly, and avoid inventing external claims?
  3. System Layer: How does the system behave end-to-end? What is the wall-clock latency, token consumption, cost per query, and error rate?

The Core Metrics, Explained Simply with Analogies

Rather than relying on abstract formulas, here are the primary evaluation metrics explained with simple analogies:

  • Correctness: The exam answer key. Does the generated response state the same factual conclusions as the reference answer? Measured via token F1 overlap or a judge model.
  • Answer Relevance: The job interview response. Did the candidate answer the specific question asked, or did they pivot into an unrelated topic?
  • Faithfulness (Grounding): The open-book test rule. Are all claims in the response directly supported by the retrieved passages? If the model includes claims absent from the text, it is ungrounded (a hallucination).
  • Context Recall: The detective's evidence sweep. Did the retriever find all the necessary clues to answer the question completely?
  • Context Precision: The signal-to-noise ratio. Are the relevant snippets ranked at the very top of the retrieved context, or are they buried beneath irrelevant chunks?
  • Retrieval Hit Rate: The library search. Did the expected source document appear anywhere in the top-$k$ returned results? Binary: yes (1.0) or no (0.0).
  • Latency: The stopwatch. Total elapsed time before the user receives the answer.

Deterministic Metrics vs. LLM-as-a-Judge

Every evaluation workflow must choose between deterministic algorithms and model judges:

  • Deterministic (Lexical) Metrics: Fast, 100% reproducible, zero API cost, and executable offline. If you run them ten times, you get the exact same score ten times. However, because they rely on token overlap, they penalize valid paraphrases and synonyms.
  • LLM-as-a-Judge: A frontier model understands semantic equivalence and nuance. It recognizes that "24 months" matches "2 years." However, LLM judges are non-deterministic, cost money, add latency, and introduce well-documented cognitive biases.

The Traps of LLM Judges and How to Calibrate Them

Using an LLM to evaluate another LLM introduces three well-documented systematic failure modes:

  1. Position / Order Bias: In pairwise comparisons, judges systematically favor whichever candidate response appears first in the prompt (Zheng et al., 2023; Wang et al., 2023). Reversing the order often flips the outcome.
  2. Verbosity Bias: Judges award higher scores to wordy, elaborate responses, even when a concise two-sentence answer was more direct and accurate.
  3. Self-Preference: Models exhibit an empirical preference for outputs generated by models from their own family (Panickssery et al., 2024).

Calibrating with Cohen's Kappa

To determine whether an LLM judge is reliable on your specific domain, you must calibrate it against human labels using Cohen's kappa (κ) (Cohen, 1960).

Simple percentage agreement is misleading because two raters will agree on many cases purely by chance. Cohen's kappa subtracts that chance agreement:

$$\kappa = \frac{P_o - P_e}{1 - P_e}$$

Where $P_o$ is observed agreement, and $P_e$ is expected chance agreement. By convention (Landis and Koch, 1977), κ below 0.40 indicates poor agreement, 0.41–0.60 is moderate, 0.61–0.80 is substantial, and above 0.81 is near-perfect. Note that these bands are conventional heuristic boundaries, not universal ground truth. Furthermore, when calibrated against a single human, κ measures agreement with that individual annotator, not absolute ground truth.

The Small-Sample Guard: When evaluating fewer than 10 labeled cases, calculating κ is statistically unreliable. A sound harness must report insufficient_labels rather than fabricating agreement.

Building a Good Test Set: Real Cases, Gold Passages, and Unanswerables

An evaluation is only as trustworthy as the test set behind it. A robust benchmark requires four elements:

  1. Realistic User Queries: Include conversational queries with typos, domain slang, and multi-part questions rather than sanitized synthetic phrases.
  2. Gold Reference Answers: Verified factual answers approved by domain experts.
  3. Reference Gold Passages: The exact source documents or paragraph IDs that contain the answer. This isolates retrieval evaluation from generation.
  4. Deliberately Unanswerable Questions: Include 15% to 20% queries that your documentation cannot answer. A reliable production bot must decline politely ("I do not have that information in my documentation"). If your dataset lacks unanswerable queries, you can never penalize guessing or reward refusal.

Why Did It Fail? Failure Taxonomy and Counterfactual Attribution

Scoring 0.20 on correctness does not explain how to fix the application. In LLM-EvalHub, we formalized a ten-category failure taxonomy executed in a fixed chronological order:

  • provider_error / timeout / empty_response: Infrastructure and API failures.
  • poor_retrieval: Supporting context was never retrieved from the knowledge base.
  • hallucination: Generated content was absent from context and contradicted the reference.
  • unsupported_claim: Answer is partially grounded, but introduces unsupported assertions.
  • incorrect_answer / missing_information / low_relevance: Well-formed response that is wrong, incomplete, or off-topic.
  • high_latency: Correct response that exceeded the latency budget.

Why ordering matters: If retrieval failed, your model had no factual basis to answer. Blaming the model for a hallucination sends engineers to edit prompt templates when the real fix is tuning chunking or retrieval parameters.

Counterfactual Failure Attribution

Observational scores describe what failed, but do not prove causality. Counterfactual attribution intervenes by re-running the failed work unit under controlled conditions:

  • ORIGINAL: The recorded failure from the standard run.
  • ORACLE_CONTEXT: Retrieved passages are replaced with gold reference text. Does the model succeed when retrieval is perfect?
  • NO_CONTEXT: Context is completely removed. Does the model answer from pre-trained memory alone?
Verdict Condition Evidence Root Cause & Remediation
RETRIEVAL_CAUSED ORIGINAL fails ∧ ORACLE passes Retrieval bottleneck: Model succeeds with gold context. Fix retrieval: tune top-$k$, chunk overlap, or use hybrid search.
GENERATION_CAUSED ORIGINAL fails ∧ ORACLE fails ∧ NO_CONTEXT fails Generation bottleneck: Model failed even with gold context. Refine prompt instructions, add few-shot examples, or upgrade model.
PARAMETRIC_KNOWLEDGE ORIGINAL fails ∧ ORACLE fails ∧ NO_CONTEXT passes Context-ignoring behavior: Model answered correctly without context, but was distracted by it. Enforce strict quote-based grounding constraints.
NOT_CONTEXT_DEPENDENT ORIGINAL passes ∧ NO_CONTEXT passes Not testing RAG: Model answered from memory alone. Reported transparently so it is not mistaken for a retrieval success.
NOT_ATTRIBUTABLE Missing reference context or trial error Cannot establish causality without gold reference passages. Safely reported rather than inferred.

Did My Change Really Help? Noise and Statistics for Beginners

If your average score moves from 0.74 to 0.77 across 20 cases after a prompt change, did your bot actually improve?

Because LLM generation is non-deterministic, a +0.03 nudge on 20 samples can easily happen by pure chance. To prevent chasing noise, use four basic statistical practices:

  • Paired Comparisons: Always compare models or prompts on the exact same test cases. Subtracting paired results removes query difficulty variance.
  • Bootstrap Confidence Intervals: Take 1,000 random resamples of paired differences to compute a 95% confidence interval. If the interval crosses zero (e.g., [-0.02, +0.08]), the difference is not statistically significant.
  • Permutation Tests: Randomly flip delta signs across thousands of permutations to calculate the probability of seeing that score by chance. If $p > 0.05$, count the result as "unchanged."
  • Flag Underpowered Samples: Testing on fewer than 8 to 10 cases lacks statistical power to distinguish real effects from noise. Explicitly flag small samples rather than presenting them as conclusive.

The Improvement Loop: From Measurement to Better Systems

Most evaluation platforms stop at a static leaderboard. A production workflow requires closing the loop:

  1. Evaluate: Run frozen experiment configurations over structured datasets across candidate models.
  2. Compare: Compute paired deltas, sample sizes, and bootstrap confidence intervals against your baseline.
  3. Diagnose: Trace failures through the taxonomy to identify root causes with linked evidence.
  4. Recommend: Rank models using multi-objective weighting that preserves metric magnitudes.
  5. Improve: Generate a follow-up experiment containing an isolated configuration tweak.
  6. Re-evaluate: Re-run test cases (or failed cases only) to verify the fix solved the issue without regressions.

What I Learned Building LLM-EvalHub

Building LLM-EvalHub taught me that the hardest part of evaluation is ensuring your instruments do not mislead you. Here are three lessons from the repository:

Lesson 1: Unavailable Is Not Zero

In an early prototype, when a dataset row lacked a reference answer, the harness assigned correctness a score of 0.0. When evaluating open-ended datasets, every model's aggregate score collapsed. Conflating "unknown" with "wrong" distorts model comparisons. If prerequisite data is missing, a metric must return available: false with a reason string and be omitted from aggregate means.

Lesson 2: One Shared Tokenizer for Metrics and Retrieval

Originally, deterministic metrics stemmed words (mapping "refunds" to "refund"), while the lexical retriever did not. The retriever failed to match documents, but context_recall credited them as matched. The metric and retriever were actively disagreeing about word identity.

Unifying both behind a single shared tokenizer (app/core/text.py) produced significant improvements on the rag_qa benchmark pack:

  • context_recall moved from 0.53 to 0.91.
  • poor_retrieval failure cases dropped from 12 down to 2.

Lesson 3: Magnitude-Preserving Normalization

My first recommender applied min-max normalization across candidate models. When comparing two models, min-max collapses every metric to 0.0 and 1.0. A tiny difference (0.90 vs. 0.88) was penalized identically to a huge gap (0.90 vs. 0.30). The solution was using measured quality values directly and scoring unbounded latency as fastest / this.

Architecture and Honest Limitations

LLM-EvalHub features a FastAPI backend, React + Vite frontend, LangGraph execution graph per work unit, 77 offline unit tests, six benchmark packs, and an offline test provider. Stated limitations: single-tenant without authentication, lexical metrics that under-credit paraphrasing, text-layer PDF parsing only, and single-annotator calibration that measures agreement with that person rather than absolute truth.

Hands-on Runnable Python Code Examples

Below are three self-contained Python examples demonstrating these concepts without external API keys.

Example 1: Deterministic Eval Harness ("Unavailable, Never Zero")

This harness scores token F1 and retrieval hit rate at $k=2$. Case 6 lacks a reference answer; it is marked unavailable and omitted from the aggregate mean. 

# Example 1: Token F1 & Hit Rate with "Unavailable, Never Zero"
def tokenize(text):
    return [w.strip(".,!?:;\"'()[]{}") for w in text.lower().split() if w.strip(".,!?:;\"'()[]{}")]

def token_f1(pred, ref):
    p_tok, r_tok = tokenize(pred), tokenize(ref)
    if not p_tok or not r_tok:
        return 0.0
    common = set(p_tok) & set(r_tok)
    if not common:
        return 0.0
    prec = sum(min(p_tok.count(t), r_tok.count(t)) for t in common) / len(p_tok)
    rec = sum(min(p_tok.count(t), r_tok.count(t)) for t in common) / len(r_tok)
    return 2 * (prec * rec) / (prec + rec)

def score_case(pred, ref, ret_srcs, exp_srcs, k=2):
    corr = {"available": True, "score": round(token_f1(pred, ref), 4)} if ref else {"available": False, "score": None}
    hit = 1.0 if any(s in ret_srcs[:k] for s in exp_srcs) else 0.0
    return {"correctness": corr, "hit_rate": hit}

dataset = [
    ("Refunds take 3 to 5 business days.", "Refunds process within 3-5 business days.", ["doc_bill"], ["doc_bill"]),
    ("Reset password from settings page.", "Go to settings to reset your password.", ["doc_auth"], ["doc_auth"]),
    ("We support USD, EUR, and GBP.", "Supported currencies: USD, EUR, GBP.", ["doc_cur"], ["doc_cur"]),
    ("Enterprise SLA guarantees 99.9% uptime.", "99.9% uptime SLA for enterprise.", ["doc_faq"], ["doc_sla"]),
    ("Contact support at support@example.com", "Email support@example.com for help.", ["doc_help"], ["doc_help"]),
    ("What are your business hours?", None, ["doc_hours"], ["doc_hours"]),  # Open-ended!
]

res = [score_case(p, r, ret, exp) for p, r, ret, exp in dataset]
valid_c = [r["correctness"]["score"] for r in res if r["correctness"]["available"]]
honest_mean = sum(valid_c) / len(valid_c)
flawed_mean = sum(r["correctness"]["score"] or 0.0 for r in res) / len(res)

print(f"Total: {len(res)}, Valid: {len(valid_c)}, Unavailable: {len(res) - len(valid_c)}")
print(f"Honest Mean Correctness: {honest_mean:.4f}")
print(f"Flawed (Zero-Filled) Mean: {flawed_mean:.4f}")
print(f"Hit Rate @ k=2: {sum(r['hit_rate'] for r in res) / len(res):.4f}")
Total: 6, Valid: 5, Unavailable: 1 Honest Mean Correctness: 0.5114 Flawed (Zero-Filled) Mean: 0.4262 Hit Rate @ k=2: 0.8333

Example 2: Cohen's Kappa Judge Calibration with Safeguard

This function calculates Cohen's kappa between human labels and judge ratings, returning insufficient_labels when $N < 10$. 

# Example 2: Cohen's Kappa with Small-Sample Safeguard
def cohen_kappa(rater_a, rater_b, min_labels=10):
    n = len(rater_a)
    if n < min_labels:
        return {"status": "insufficient_labels", "kappa": None, "n": n}
    
    cats = sorted(list(set(rater_a) | set(rater_b)))
    po = sum(1 for a, b in zip(rater_a, rater_b) if a == b) / n
    pe = sum((rater_a.count(c) / n) * (rater_b.count(c) / n) for c in cats)
    kappa = (po - pe) / (1.0 - pe) if pe < 1.0 else 1.0
    return {"status": "ok", "po": round(po, 4), "pe": round(pe, 4), "kappa": round(kappa, 4), "n": n}

# Small sample (N=6) triggers safeguard
small_human = ["PASS", "PASS", "FAIL", "PASS", "FAIL", "PASS"]
small_judge = ["PASS", "PASS", "PASS", "PASS", "FAIL", "PASS"]
print("Small Sample (<10):", cohen_kappa(small_judge, small_human))

# Calibrated sample (N=15)
human = ["PASS", "PASS", "FAIL", "PASS", "FAIL", "PASS", "FAIL", "PASS", "PASS", "FAIL", "PASS", "FAIL", "PASS", "PASS", "FAIL"]
judge = ["PASS", "PASS", "PASS", "PASS", "FAIL", "PASS", "FAIL", "PASS", "PASS", "FAIL", "FAIL", "FAIL", "PASS", "PASS", "FAIL"]
res = cohen_kappa(judge, human)
print(f"Calibrated Sample (N={res['n']}): Observed Po={res['po']}, Chance Pe={res['pe']}, Kappa={res['kappa']}")
Small Sample (<10): {'status': 'insufficient_labels', 'kappa': None, 'n': 6} Calibrated Sample (N=15): Observed Po=0.8667, Chance Pe=0.52, Kappa=0.7222

Example 3: Paired Bootstrap Confidence Interval on Metric Deltas

This snippet compares Model A and Model B across 12 paired cases using 1,000 bootstrap resamples to check if an improvement is statistically significant. 

# Example 3: Paired Bootstrap Confidence Interval (NumPy)
import numpy as np
np.random.seed(42)

scores_a = np.array([0.72, 0.85, 0.60, 0.91, 0.45, 0.78, 0.88, 0.65, 0.52, 0.94, 0.70, 0.82])
scores_b = np.array([0.78, 0.88, 0.62, 0.95, 0.58, 0.85, 0.90, 0.71, 0.50, 0.96, 0.77, 0.89])

deltas = scores_b - scores_a
boot_means = [np.mean(np.random.choice(deltas, size=len(deltas), replace=True)) for _ in range(1000)]

ci_lower = np.percentile(boot_means, 2.5)
ci_upper = np.percentile(boot_means, 97.5)
is_sig = (ci_lower > 0) or (ci_upper < 0)

print(f"Observed Mean Delta: {np.mean(deltas):+.4f}")
print(f"95% Bootstrap CI: [{ci_lower:+.4f}, {ci_upper:+.4f}]")
print(f"Verdict: {'Statistically Significant Improvement' if is_sig else 'Inconclusive / Unchanged'}")
Observed Mean Delta: +0.0475 95% Bootstrap CI: [+0.0275, +0.0675] Verdict: Statistically Significant Improvement

Environment & Verification: Executed in Python 3.11.9 with NumPy 1.23.5. All printed outputs reflect real execution runs.

A Starter Checklist to Evaluate Your Own RAG or Q&A Bot

Before pushing prompt changes or updating your retrieval settings, run through this 10-point checklist:

  1. Curate a frozen benchmark dataset: Prepare at least 30 representative test cases before modifying prompts.
  2. Measure retrieval and generation separately: Track context recall and hit rate independently from answer correctness.
  3. Include unanswerable queries: Ensure at least 15% of queries cannot be answered by your knowledge base to test refusal behavior.
  4. Treat missing reference scores as unavailable: Never average missing reference answers as 0.0.
  5. Unify tokenization logic: Verify that tokenizer stemming and word boundaries match across retriever and metrics.
  6. Calibrate LLM judges against human labels: Verify Cohen's kappa (κ > 0.60) before accepting judge scores.
  7. Test for judge order and verbosity bias: Swap candidate positions to ensure judges do not merely prefer the first or longest response.
  8. Use paired comparisons: Evaluate candidates on identical test cases rather than independent batches.
  9. Compute confidence intervals: Verify that the 95% bootstrap interval on metric deltas does not cross zero before declaring victory.
  10. Link failures to evidence: Ensure every failure record stores the question, retrieved context, and raw model response.

Frequently Asked Questions

What are LLM evals?

LLM evals are structured benchmarks that score how well a language model or RAG application handles a curated set of prompts. Rather than judging an application by checking a few queries manually, evals measure statistical distributions of factual correctness, relevance, grounding, and latency across hundreds of test cases.

What is the difference between RAG evaluation and normal LLM evaluation?

Standard LLM evals test a model's raw pre-trained knowledge and instruction-following capabilities. RAG evals test a multi-component system: the retriever (which chunks and surfaces context), the generator (which synthesizes an answer strictly from that context), and the operational latency of the combined pipeline.

Can I trust LLM-as-a-judge?

Only after calibrating it. LLM judges understand semantic nuance, but they exhibit proven biases toward verbosity, answer ordering, and outputs generated by their own model family. You should always measure your judge's agreement against human-annotated samples using Cohen's kappa before using it as a decision-maker.

How many test cases do I need?

You can start debugging with 20 to 30 well-constructed cases. To detect whether a prompt modification or model switch made a statistically significant improvement, aim for at least 30 to 50 paired cases. Testing on fewer than 8 to 10 cases yields high statistical noise and underpowered comparisons.

Which metric should I start with?

For RAG applications, start by measuring retrieval hit rate (or context recall) and faithfulness. If your retriever does not locate the right document, your generator cannot succeed. If your generator creates claims unsupported by the retrieved text, you have a hallucination problem.

Conclusion

Moving from interactive playgrounds to reliable production systems requires trading casual impressions for empirical measurements. Keep these three core principles in mind:

  • Isolate your components: Never debug a generator before verifying that your retriever delivered the required context.
  • Report missing data honestly: Never score unannotated test cases as zero; report unknown values as unavailable to keep aggregate leaderboards honest.
  • Verify improvements with statistics: Use paired comparisons and confidence intervals so you stop optimizing for random model stochasticity.
